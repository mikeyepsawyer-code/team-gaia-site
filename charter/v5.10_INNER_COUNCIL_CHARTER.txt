At the end of every session Thomas speaks as Council Chair and runs a
closing check. This is not optional. It happens every session.

SECTION 1D — MASTER FILE VERSIONING & COLOR-MARKUP PROTOCOL
(added v5.6, August 11 2026 — Michael's fix for scattered notes)

THE PROBLEM THIS FIXES: loose brainstorm notes and XPOLL snippets have been
piling up unlinked in Drive root, in Inner Council Projects root, and in
Inner Council/ — with no consistent home and no reliable way to know which
copy is current. This stops now.

WHERE MASTER COPIES LIVE (no exceptions):
 GitHub is the single home for every book's master content: manuscript
 text, cover previews, cover source photos, finished cover art, and cover
 construction instructions. Drive never holds an unlinked master — only
 working brainstorm documents scoped to one specific Books/[Title]/ folder,
 or session notes in Inner Council/. Nothing lives loose in Drive root or
 in Inner Council Projects root. If a note doesn't have an obvious book
 home yet, it goes in Inner Council/ as a dated session note — never root.

THE EDIT PROCEDURE (mandatory, every time a book contents master file is
touched):
 1. COPY FIRST. Before changing anything, copy the existing master file
    under a new version name (v[X.X]_[TITLE]_WORKING or similar). Never
    edit the master file in place.
 2. COLOR-MARK. In the new working version, Claude's additions/edits are
    marked blue, Michael's are marked red. In native Google Docs, use
    real text color. In plain-text files, use inline tags —
    [CLAUDE]...[/CLAUDE] and [MICHAEL]...[/MICHAEL] — since plain text
    can't carry actual color.
 3. PUSH TO GITHUB. The new working version goes to GitHub immediately,
    alongside (not replacing) the current master. Keep it there through a
    couple of further iterations — don't erase a working version the
    same session it's created.
 4. MIRROR TO DRIVE. Copy the same working version into the book's own
    Books/[Title]/ folder in Drive — never root, never Inner Council
    Projects root. Delete any older working copies already sitting in
    that Drive folder, or if deletion isn't available, tell Michael
    exactly which ones to remove.
 5. AWAIT MICHAEL'S PASS. Michael edits and sends the working version back.
 6. FINALIZE. On return, convert every red and blue passage to plain black
    text — no more color markers or tags — and re-tag the file as the
    new master copy (drop the WORKING suffix, bump the version number).
    Push the finalized master to GitHub. Only a file that has been through
    this full cycle earns plain "master" status; anything mid-cycle stays
    labeled WORKING so it's never mistaken for canon.

RETENTION: same spirit as the charter policy (Section 7) — keep one or
two prior working iterations as a safety net, not an archive. Once a
master is finalized and confirmed working, older working copies get
cleared per steps 4 and 6.

SECTION 1E — SESSION-OUTPUT PERSISTENCE (added v5.7, August 11 2026)
(root cause of the lost Sapiens Cyberneticus chapters, closed)

WHAT HAPPENED: On May 24, Claude wrote ~5,000 words of full chapter
prose for Sapiens Cyberneticus, showed it to Michael as a downloadable file
via present_files, then separately created and saved to Drive a
short, condensed, headers-only outline under the book's actual
filename. The full prose was never itself pushed to Drive or
GitHub. When the session ended, it was gone from every durable
location — recoverable months later only by searching the raw
chat transcript. This must not happen again.

THE RULE: WHAT'S SHOWN IS WHAT'S SAVED.
 Any time Claude generates substantive original content and
 presents it to Michael — whether via present_files, an artifact,
 or a long chat reply — the exact same content, in full, must be
 the version persisted to Drive and/or GitHub per Section 1D. Not
 a summary. Not a condensed outline standing in for the whole. Not
 "the headers, with a note that the full version exists elsewhere."

 If Claude wants to ALSO save a shorter/condensed companion version
 (an index, a headers-only outline, a quick-reference card), that
 is fine — but it is saved as an ADDITIONAL file with its own
 name, never as a silent substitute that occupies the filename the
 full version should have had.

SESSION-OUTPUTS DIRECTORY IS NOT STORAGE:
 /mnt/user-data/outputs (and any present_files call) is ephemeral
 to the session. It is how Michael sees and downloads a file in the
 moment. It is never itself the save. If a file only exists there
 by the time Thomas runs the closing check, treat it as unsaved
 work per Section 1B, not as "already delivered."

THOMAS'S CLOSING CHECK, EXTENDED:
 When Thomas confirms files saved (Section 1C, check 1), he also
 confirms word-count / scope parity — that what got saved to
 Drive/GitHub is the same substance as what was shown in the
 session, not a smaller stand-in for it. If the two don't match, he
 says so by name before the session closes.

SECTION 1F — PROACTIVE VALUE-FLAGGING & THE XPOLL/ OVERFLOW FOLDER
(added v5.8, August 16 2026)

THE RULE: over the course of any session, if Claude judges something
Michael has said, or something drafted together, to be unusually
resonant, quotable, or valuable to the wider library — beyond whatever
immediate task prompted it — Claude names this out loud in the moment,
rather than silently filing it away or letting it pass unremarked.
Example: an unplanned, vivid image or turn of phrase that surfaces
mid-conversation and seems to want a home somewhere in the catalog.

THEN: Claude and Michael discuss briefly, right then, where it
belongs — not deferred to a private "note to self" for later.

THEN: it gets saved per that discussion. If a clear book destination
exists, insert directly into that book's manuscript on GitHub (per the
Aug 15 2026 cross-pollination workflow — no separate staging note when
a direct home is available). If no clear destination exists yet, or it
plausibly serves multiple books, it goes into the xpoll/ folder at
repo root rather than a Drive note.

THE xpoll/ FOLDER: a dedicated GitHub folder for exactly this kind of
banked material — resonant fragments, images, or lines without an
immediate placement. One file per entry, dated and named for its
content (matching the existing charter/XPOLL_*.txt naming convention,
e.g. xpoll/2026-08-16_example-name.txt), status marked RED until
Michael approves a destination and it migrates into a manuscript. This
replaces Drive as the fallback staging location going forward. The two
charter/XPOLL_*.txt files predating this folder (heart-verb-nature,
four-words-icon) may be migrated here for consistency at a later
session; no urgency.

WHAT THIS IS NOT: a mandate to interrupt every session with commentary
on every sentence. The bar is "this could stand alone or travel to
another book," not "this was a nice sentence." Claude uses judgment
here the way Claude already uses judgment elsewhere — flagging should
feel like a colleague noticing something, not a hall monitor grading
the conversation.

SECTION 1G — SOURCE COMPLETENESS CHECK BEFORE SEEDING A MANUSCRIPT
(added v5.9, August 16 2026)

THE PROBLEM THIS FIXES: twice in one session, Claude built a "seed"
manuscript for a book from an outline or Drive notes alone, missed
real, finished prose that already existed elsewhere (first in
enchante-nike-preview.html, then again in cultivating-chi-preview.html),
and had to be corrected by Michael after the fact in both cases.

THE RULE: before creating any new manuscript file for a book that
doesn't yet have one on GitHub, check ALL of the following — not just
the first one that returns something:
 1. manuscripts/[book-slug]/ on GitHub
 2. The book's own Drive folder
 3. [book-slug]-preview.html (or similarly named preview page) on
    GitHub. Preview pages are hand-written, full prose, and a genuine
    primary source — not a display layer summarizing content that
    lives somewhere else. Never assume a preview page's text is a
    condensed version of some other, more complete document. It may
    be the only complete document that exists.
 4. Cover build notes and any other book-tagged file in the repo,
    briefly, in case they reference prose not yet located.

Only after checking all of the above does Claude conclude no draft
exists and proceed to build from outline/notes alone.

RETENTION, restated and generalized from the pattern above: until
Claude is certain which version is current and complete, nothing gets
deleted or silently overwritten. When two candidate sources for the
same book's content are found (an outline and a preview page, two
Drive docs describing the same material, etc.), the default is to
preserve both, surface the discrepancy to Michael, and let him decide
— not to pick one and discard the other on Claude's own judgment. This
extends Section 1D's retention policy: "keep one or two prior working
iterations" applies to genuinely superseded working copies produced
during an edit cycle, not to independent sources that haven't yet been
reconciled against each other.

SECTION 1H — UPDATE CADENCE FOR CHARTER, PROJECT KNOWLEDGE & TOOLS
(added v5.10, August 23 2026)

WHY THIS EXISTS: as the project has grown, three different kinds of
"memory" have accumulated — this charter, Claude's project knowledge
(memory system), and the tools/skills folder on GitHub — each updating
on its own rhythm. This section makes that rhythm explicit so nothing
drifts silently.

THE CHARTER updates immediately whenever a governance-level decision is
made: a new protocol, a canon rule, a standing workflow trigger, a
retention policy. It does not update on a schedule and it is never
batched into a periodic review — the moment a rule is established is
the moment it goes in, in the same session. Minor wording fixes and
typos are the one exception: hold those and fold them into the next
substantive edit rather than spending a version bump on them alone.
Every substantive edit bumps the version number by 0.1 and is dated
inline in its section header, exactly as this section is.

CLAUDE'S PROJECT KNOWLEDGE (memory) updates automatically in the
background from conversation history and is not manually versioned
like the charter. Michael can also direct explicit memory edits at any
time ("please remember," "please forget"). The Section 1C session-close
protocol feeds it context, but what actually persists is the memory
system's call, not a file Claude edits directly.

TOOLS/SKILLS (cover_build.py, gaia_orient.py, and anything added to
tools/ going forward) update whenever a real bug is found or a
workflow genuinely improves — never on a schedule, and never
speculatively. Each script is fetched fresh at the start of any session
that touches it (per existing practice) so drift is caught early.
Every meaningful revision gets a one-line comment at the top of the
script noting what changed and why, so the history is visible in the
file itself, not just in git.

CHARTER AND TOOLS ARE CATALOG-WIDE BY CONSTRUCTION: there is one
charter and one tools/ folder for the entire repo, used by every book
including Scribe and Sapiens Cyberneticus — not per-book copies that
need manual mirroring. A protocol or tool fix made here already applies
everywhere the moment it's pushed. Nothing needs to be separately
propagated.

CONTENT BOUNDARY — CHARTER VS. PROJECT KNOWLEDGE: because the charter
and tools are catalog-wide and, in principle, could be shared outside
this project as a clean template, they stay generic: protocols,
standards, workflows, catalog structure, technical infrastructure.
Personal, sensitive, or identifying information about Michael or his
family — health details, life circumstances, anything that isn't
needed to run the work itself — belongs in Claude's project knowledge
only, never in the charter or in any file pushed to GitHub. If
personal context is genuinely needed to inform how Claude works with
Michael, it lives in memory, not in a version-controlled document.

NOTE ON SECTION 2 BELOW: it currently holds specific medical and family
information (Michael's son, Michael's wife) that predates this rule and
sits exactly where this rule says it shouldn't. Flagging this rather
than editing it unprompted, since it's sensitive family health content
and because GitHub version history means removing it in a new commit
doesn't erase it from prior commits — Michael should decide how he
wants that handled (move to memory and scrub history, move to memory
and leave history as-is since the repo is private, or leave as is)
before Claude touches it.
