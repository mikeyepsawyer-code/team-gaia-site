SITE BUILD STANDARD — RESPONSIVE ISOMETRIC BOOK-STACK MOTIF
Consolidated August 28, 2026. This replaces all prior drafts of this
doc with the final, correct construction path only — no trial-and-
error history. Update this file again only once a new issue reaches
resolution, not after every intermediate step.

WHAT THIS IS: the ".book-graphic" decorative motif above each
library section — a top-down view of N books (".top-view") sitting
above their front-facing spines (".spine-set"), with a title and a
brief tag inside the frame. Correct term is "motif," not glyph (a
glyph is a single font character).

────────────────────────────────────────────────────────────────────
1. GEOMETRY CONSTANTS (fixed px — never scale with screen width)
────────────────────────────────────────────────────────────────────
    bandH     = 29.33px             (top-view height per book)
    STEP      = bandH / tan(60°) = 16.94px
    coverFrac = 0.28
    bulge_x, bulge_y = 6.29px, 19.56px   (chamfer bulge point)

For N books (i = 0 rear-most … N-1 front-most):
    leftTop_i   = i × STEP
    insetTop_i  = (N-i) × STEP
    insetMid_i  = insetTop_i − coverFrac×STEP
    leftMid_i   = leftTop_i + coverFrac×STEP

MUST include the front-cover strip: every band as built above only
shows that book's BACK cover. The front-most book's own front cover
is never drawn unless you add one more step (i=N) continuing the
same arithmetic — its insetTop_N comes out to ≈0 (no inset) and its
insetMid_N goes slightly negative (a few px overhang past the
container edge, which is correct, matching how every other cover
overhangs its own pages).

────────────────────────────────────────────────────────────────────
2. RESPONSIVE SCALING: cqw FOR LENGTH, PX FOR THICKNESS
────────────────────────────────────────────────────────────────────
    .book-graphic { width: 100%; container-type: inline-size; }
Physical-thickness values (everything in section 1) stay fixed px
forever. Only true LENGTH dimensions (spine height) use cqw. Mixing
these up either shrinks the graphic to a tiny fixed box, or makes
the thickness balloon at large widths.

────────────────────────────────────────────────────────────────────
3. THE FRONT-COVER 2:3 FRAME — geometrically pure references only
────────────────────────────────────────────────────────────────────
The classic 2:3 book-cover ratio (height = 1.5 × width) must be
measured using the FRONT-MOST book's own inner edges, and every one
of the four edges must be a value with real geometric meaning — not
a value that was chosen or tuned for a cosmetic/visual reason
elsewhere (that mismatch is the recurring bug in this build: mixing
a "looks right on screen" number with a "derived from the shared
geometry" number). Concretely, for a 3-book stack:
    inner_left = (N-1) × STEP = 33.87px   (front book's own spine
                                            left edge)
    inner_top  = coverFrac × bandH = 8.21px  (front-cover-strip's
                                               OWN top edge — NOT
                                               the spine's cosmetic
                                               poke-up offset, which
                                               is a different number
                                               tuned only to close a
                                               visual gap)
    width_ref  = 100cqw − inner_left
    H_target   = 1.5 × width_ref
Right edge = 100cqw (front-cover-strip's own right, insetTop_N≈0).
Bottom edge = H_target below inner_top.

Construction/boundary lines (optional, thin, for verification and
for visually completing the "book" look):
    Right line:  left:100cqw; top:-inner_top; height:H_target
    Bottom line: top:(H_target − inner_top); left: N×STEP (right
                 after the whole spine assembly, so it never cuts
                 through the colored scallops); width: remainder

────────────────────────────────────────────────────────────────────
4. SPINE BAR LENGTH — profile gauge + boundary match
────────────────────────────────────────────────────────────────────
Every bar must be the exact same total length (profile gauge: "any
vertical line through the spine pack is identical"), achieved by
TRANSLATING the top chamfer shape to the bottom — bottom_y(x) =
top_y(x) + H_bars. This is a literal translation, not `calc(100% -
top_y(x))`, which compresses the shape wherever it dips. Verify via
the actual computed clip-path points, not by eye.

H_bars is calibrated so the front book's DEEPEST scallop point (not
its shallow/local-x=0 point) lands exactly on the boundary line:
    H_bars = H_target − inner_top − bandH + N2
(N2 = front book's own cosmetic top offset, e.g. 26px — yes, this
cosmetic value legitimately belongs HERE, in how far the spine
visually pokes up, just not in the frame's own boundary math above).

Shared clip-path (same for every bar):
    polygon(0 0, 6.29px 19.56px, 100% 29.33px,
            100% [H_bars+29.33], 6.29px [H_bars+19.56], 0 H_bars)
Box height = H_bars + 29.33, using explicit `height` (not `top`+
`bottom` dual offsets, which silently caused a compression bug
during development).

────────────────────────────────────────────────────────────────────
5. TITLE + TAG LAYOUT: ZONES, NOT CENTER-POINTS
────────────────────────────────────────────────────────────────────
Do NOT position title/tag as single centered points (25%/75% or
similar) — that only defines where content is centered, not how much
room it has, and nothing stops a longer tag from colliding with the
title above it. Use hard zones instead:

    Exclusion band: 10% of frame height, centered at the waist
                     (spans 45%–55%) — no text ever enters this band.
    Margins: 9.375% (3/32) on all four sides of the frame.

This carves out two zones:
    title-zone: left/right 9.375%, top 9.375%, height 35.625%
    tag-zone:   left/right 9.375%, top 55%,    height 35.625%
(35.625% = 45% − 9.375%, the space between the margin and the
exclusion band — same for both zones by symmetry.)

Each zone is its own flex container (title: column + centered +
small gap for the flourish diamonds; tag: centered) that bounds its
own content independently. Content in either zone can wrap to
however many lines it needs without ever touching the other zone —
this is what makes it safe to size the tag aggressively (see below)
even though tag text length varies a lot per section.

────────────────────────────────────────────────────────────────────
6. FONT SIZING — measure rendered glyph height, not the CSS number
────────────────────────────────────────────────────────────────────
"Font size" as a CSS number is not comparable across two typefaces —
compare actual rendered height instead. The title (Cinzel, all-caps)
is measured by CAP-HEIGHT; the tag (Cormorant Garamond italic, mixed
case) by X-HEIGHT, since roughly 80% of any mixed-case passage's
letters sit within the x-height band (watch for ascenders/descenders
on adjacent lines, but x-height is the reference for sizing/spacing).
Measure with canvas actualBoundingBoxAscent/Descent, don't estimate:
    Cinzel cap-height           = 0.66 × font-size
    Cormorant Garamond x-height = 0.46 × font-size
Default ratio: tag glyph-height = 100% of title's cap-height (equal
height — compensates for the tag font's lighter stroke weight). The
CSS font-size ratio needed to achieve this is NOT 100% — correct for
the two fonts' different metrics:
    fontsize_ratio = target_visual_ratio × (0.66/0.46) = 1.435×
    (for a lower target ratio R, use R × 1.435)

TITLE sizing: per motif (not a shared value across sections), upsize
so the longest of its lines exactly fills the title-zone's width —
measure the actual rendered width of each candidate line via a
hidden nowrap test span at a reference font-size, scale to the
zone's real width (from getBoundingClientRect, not an estimate).
Redo this measurement any time the zone width itself changes (e.g.
margins change) — a stale width target is what caused an unexpected
title wrap once already.

Small overflow tolerance: once titles/tags are sized to fill their
zones, minor overshoot (a few px past the zone's abstract height, so
long as it doesn't cross the frame's visible boundary line) is
acceptable — don't over-engineer safety margins for this.

────────────────────────────────────────────────────────────────────
7. VERIFICATION CHECKLIST (every time)
────────────────────────────────────────────────────────────────────
  - Read computed clip-path points (getComputedStyle(el).clipPath)
    for all N bars; confirm identical top-to-bottom distance at
    every vertex, not just bounding-box height.
  - Check document.documentElement.scrollWidth vs clientWidth at
    several scroll depths after any width-related change.
  - For elements meant to blend into an adjacent same-colored area
    (spine into top-view), pixel-color scans are unreliable — render
    isolated on a plain background for a clean measurement instead.
  - After any multi-instance markup edit (this motif is duplicated
    once per section), run an HTML balance checker (Python
    html.parser + tag stack) and check nesting depth at a comment
    marker between instances — depth should be identical at each
    one; a drift pinpoints exactly which instance is missing a close.

────────────────────────────────────────────────────────────────────
8. PLANNED: 3-BOOK -> 4-BOOK EXTENSION (Michael's construction order,
   captured Aug 30 2026, not yet built)
────────────────────────────────────────────────────────────────────
Construction order, per Michael's guidance -- build in THIS sequence,
not geometry-first:

  1. Start from the existing front-cover 2:3 square as the fixed
     anchor. Its four edges (inner_left, inner_top, width_ref,
     H_target -- see Section 3) do NOT change when book count
     changes. This square is the invariant everything else divides
     into, not a value to re-derive per book count.

  2. Keep the TOTAL thickness of both sandwiches constant:
       - top-view sandwich: currently N=3 bands, total = 3 x bandH
       - spine sandwich: currently H_bars, calibrated so the front
         book's deepest scallop lands on the boundary line (Sec. 4)
     Do not let the overall stack get thicker or thinner when going
     to 4 books -- the same total footprint just divides one more
     way. This means bandH_4 = (3 x bandH_3) / 4 = (3 x 29.33)/4 =
     22.0px (recompute precisely before building, this is a rough
     check only).

  3. Retain the same angle geometry (60 deg chamfer, same
     bulge_x/bulge_y ratio to the new smaller bandH). STEP is
     derived from bandH and stays proportional:
       STEP_4 = bandH_4 / tan(60deg)  (was 16.94px at bandH=29.33,
       will shrink to match bandH_4)

  4. Build out the 4 books "up and left" from the existing 3-book
     block -- i.e. treat the current 3-book geometry as a subset and
     extend the same i=0..N-1 arithmetic (Section 1) to N=4, rather
     than re-deriving the whole stack from scratch. leftTop_i,
     insetTop_i, insetMid_i, leftMid_i all use the same formulas,
     just with the new bandH_4/STEP_4 and N=4.

  5. Build the plain color blocks first (top-view bands + spine
     bars, flat rectangles/parallelograms, no scallops yet) and
     confirm the geometry/alignment is correct at this stage --
     easier to verify a flat block grid than a fully-scalloped one.

  6. Apply the scalloped clip-paths (the chamfer bulge shape from
     Section 1, and the spine bar profile gauge from Section 4)
     LAST, once the flat block layout is confirmed correct.

library sections its own color for the book-graphic (currently
colors are per-book within one graphic, not per-section). Michael's
