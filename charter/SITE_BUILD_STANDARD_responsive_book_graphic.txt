SITE BUILD STANDARD — RESPONSIVE ISOMETRIC BOOK-STACK GRAPHIC
Rewritten August 28, 2026 to lead with the straightforward build
path. (Earlier version kept below as "gotchas" reference — the
mistakes are worth knowing, but build it this way and you won't
make them.)

WHAT THIS IS
The ".book-graphic" motif used above each library section: a
top-down view of N stacked books (".top-view") sitting directly
above their front-facing spines (".spine-set"). Correct proper term
for this kind of illustrative element is a "decorative motif" (or
just "graphic") — not a glyph. A glyph is a single character/symbol
in a font; this is a multi-part illustration.

────────────────────────────────────────────────────────────────────
THE STRAIGHTFORWARD BUILD PATH (for N books, here N=3)
────────────────────────────────────────────────────────────────────

STEP 1 — Pick the base geometry constants (all fixed px, representing
physical thickness — these never scale with screen width):
    bandH   = 29.33px         (top-view height per book)
    STEP    = bandH / tan(60°) = 16.94px   (horizontal chamfer run)
    coverFrac = 0.28          (fraction of a band that's spine-edge
                                "cover" vs. the wider "pages")
    bulge_x = 0.667×STEP - 5  = 6.29px     (chamfer bulge point)
    bulge_y = 0.667×bandH     = 19.56px

STEP 2 — Build the top-view: N stacked ".stack-band" divs (bandH
tall each), each with a ".band-cover" (coverFrac×bandH tall) and
".band-pages" strip beneath it. Book i (0=rear-most, N-1=front-most)
uses these per-band offsets, all multiples of STEP:
    leftTop_i   = i × STEP
    insetTop_i  = (N-i) × STEP        (right-side inset, top of band)
    insetMid_i  = insetTop_i - coverFrac×STEP   (inset at cover/pages
                                                  boundary)
    leftMid_i   = leftTop_i + coverFrac×STEP
This produces the familiar stair-stepped parallelogram look.

STEP 3 — DO NOT FORGET THE FRONT-COVER STRIP. Every band as built in
step 2 only shows that book's BACK cover — the strip drawn is what
peeks out from behind the book in front of it. The very front-most
book's own FRONT cover is never drawn by that loop, because nothing
is in front of it to justify omitting it. Add ONE more strip,
continuing the same arithmetic one step further (i=N):
    leftTop_N  = N × STEP     (≈ full width — i.e. no inset, insetTop_N≈0)
    insetMid_N = insetTop_N - coverFrac×STEP   (comes out slightly
                 NEGATIVE — this strip legitimately poking a few px
                 past the container's right edge is correct, matching
                 how every other cover overhangs its own pages)
Give this strip height = coverFrac×bandH (same as a normal cover, no
pages beneath it) and the front-most book's color.

STEP 4 — Container setup for full-width responsiveness:
    .book-graphic { width: 100%; container-type: inline-size; }
This unlocks `cqw` units (1cqw = 1% of THIS element's own rendered
width). RULE: physical-thickness values (everything from step 1)
stay in fixed px forever. Only true LENGTH dimensions (the spine's
own height) use cqw, so they scale with actual screen width while
thickness stays constant. Mixing these up either shrinks the whole
graphic to a tiny fixed box, or makes the thickness balloon
absurdly wide.

STEP 5 — The 2:3 "front cover" reference. This is the step most
likely to go wrong. The classic 2:3 book-cover ratio (height = 1.5 ×
width) must be measured using the FRONT-MOST book's own inner edges
— not the rear book's, not the whole graphic's outer bounds:
    inner_left = (N-1) × STEP     (front book's own left offset)
    inner_top  = front book's own top poke-up offset (see step 6)
    width_ref  = 100cqw - inner_left
    H_target   = 1.5 × width_ref
Using the wrong book's edge (e.g. grabbing whichever K value is
first in the CSS) silently produces a mis-proportioned spine that
LOOKS plausible but isn't actually 2:3.

STEP 6 — Position the spine bars. Each bar i needs a "poke-up" (top
offset) so its color visually continues into its OWN matching band
in the top-view above:
    top_offset_i = (N-1-i) × bandH     (rear book pokes up the most)
Bar width = STEP (16.94px), left = i × STEP.

STEP 7 — Bar length: the profile-gauge property + the front-cover
boundary, together. Two requirements stack here:
  (a) PROFILE GAUGE: every bar must be the exact same total length
      (so "any vertical line through the spine pack is identical").
      Achieved by translating the SAME top-chamfer shape to the
      bottom: bottom_y(x) = top_y(x) + H_bars. This is a literal
      translation — NOT `calc(100% - top_y(x))`, which compresses
      the shape wherever it dips (verify by reading the actual
      computed clip-path points, not just eyeballing it).
  (b) BOUNDARY MATCH: the front book's DEEPEST scallop point (not
      its shallow/local-x=0 point) should land exactly on the 2:3
      boundary — so the whole assembly reads as fitting inside the
      rectangle rather than overshooting it. Since the scallop's own
      depth is `bandH` (29.33px) below the flat reference, set:
          H_bars = H_target - bandH
      then each bar's own box height = H_bars + bandH (to hold the
      full translated shape), positioned via explicit `height`
      (not `top`+`bottom` dual offsets, which silently caused a
      compression bug during development).

STEP 8 — Chamfer/scallop clip-path (shared by all bars, same values
regardless of which book): 
    polygon(0 0, 6.29px 19.56px, 100% 29.33px,
            100% [H_bars+29.33], 6.29px [H_bars+19.56], 0 H_bars)
(bracketed values are calc() expressions mixing cqw and px.)

STEP 9 — Optional boundary lines (thin, for visually completing the
"book" look / verifying the construction): 
    Right line:  left:100cqw; top:-inner_top; height:H_target
    Bottom line: top:(H_target - inner_top); left: N×STEP (i.e. right
                 after the whole spine assembly ends, so the line
                 doesn't cut through the colored scallops); width:
                 remaining space to the right edge.

────────────────────────────────────────────────────────────────────
VERIFICATION (do this before calling it done, every time)
────────────────────────────────────────────────────────────────────
  - Read the actual computed clip-path points via Playwright
    (`getComputedStyle(el).clipPath`) for all N bars and confirm the
    top-to-bottom distance is IDENTICAL at every vertex. Bounding-box
    height alone doesn't prove this — the shape can still be wrong
    even when the box size is right.
  - Check `document.documentElement.scrollWidth` vs `clientWidth` at
    several scroll depths after ANY width-related change — a single
    miscalculated calc() or an unclosed div silently breaks layout
    far downstream of where you were actually working.
  - Pixel-color scans are unreliable where a poking-up element is
    SUPPOSED to blend into an adjacent same-colored area (the spine
    into the top-view is the whole point). For a clean pixel
    measurement, render the element isolated on a plain background
    instead of trying to threshold it out of the full page.

────────────────────────────────────────────────────────────────────
MARKUP: MULTI-INSTANCE EDITING DISCIPLINE
────────────────────────────────────────────────────────────────────
This motif is duplicated once per section (currently 4x) via
str_replace edits across index.html. A single missing closing </div>
in one instance doesn't crash anything — it silently nests every
subsequent element one level deeper, which shows up as unrelated
overflow far downstream. After any multi-instance markup edit, run
an HTML balance checker (Python html.parser + tag stack) and check
NESTING DEPTH at a comment marker between each instance — depth
should be identical at each one. A drifting number pinpoints exactly
which instance is missing a close.

────────────────────────────────────────────────────────────────────
TITLE + TAG COMPOSITION: THE FIGURE-EIGHT RULE
────────────────────────────────────────────────────────────────────
Added after the section titles/tags were finalized. Within the
front-cover frame (the area right of the spines, bounded by the
optional boundary lines from step 9), the title and its tag are
each their own focal point, not one clustered block.

Picture a large figure-eight (∞) centered in the frame, its two
loops stacked vertically. The CENTER of each loop is where that
element's centerpoint should land:
    title center: 25% down the frame height
    tag center:   75% down the frame height
Implemented via two independently absolute-positioned children of a
".content-frame" wrapper (left:58px/right:0/top:0/bottom:0, matching
the spine's own padding-left), each using top:25%/75%; left:50%;
transform:translate(-50%,-50%) — NOT a single centered flex column,
which clusters both elements together with no real separation.

DEFAULT SIZE RATIO: tag font-size = 50% of that section's OWN title
font-size (same percentage applied to the clamp's min/cqw/max terms
alike), not a flat tag size shared across sections regardless of how
big that section's title is. If a third tier (an epigraph/quote) is
ever added inside the frame, extend the same modular-scale logic
rather than picking an arbitrary size.
